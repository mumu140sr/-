# シフト自動生成アプリ

飲食・サービス業向けの **月間シフト表を自動で作るアプリ** です。
スタッフの公休数・有給・担当できるシフト・個人の希望を登録しておくと、
ルールを守った1ヶ月分のシフト表を自動で組み立てます。

- **アプリを開く** → https://mumu140sr.github.io/-/
- **使い方マニュアル** → https://mumu140sr.github.io/-/manual.html

## 1. はじめに知っておくこと

**このフォルダに入っているのは「アプリの設計図（プログラム）」だけです。**
実際に作ったシフト表やスタッフ名簿は、ここには入っていません。
それらは **使っている人のパソコンのブラウザの中** に保存されています。

> 料理でたとえると、ここにあるのは **レシピ** です。
> **冷蔵庫の中身（データ）は、各自のパソコンの中** にあります。

---

## 2. このアプリの特徴

### サーバーがありません

普通の業務システムは、どこかのサーバーで動いています。
このアプリは **ブラウザの中だけで完結** しています。

そのため、こうなっています。

| | このアプリ |
|---|---|
| 月額費用 | **0円** |
| サーバーの管理 | **不要** |
| データが外部に送られる | **ない** |
| 勝手に止まる | **ほぼない** |

**誰も触らなければ、何年でも同じように動き続けます。**

### 計算エンジンを積んでいます

シフトを組むのに **HiGHS** という数理最適化エンジン（無料・オープンソース）を使っています。
`js/vendor/` に入っていて、これもブラウザの中で動きます。
インターネットに計算を投げているわけではありません。

## 3. 画面の流れ

左のメニューの順番どおりに入力していけば、シフトが作れます。

| | 画面 | やること |
|---|---|---|
| ① | 基本設定 | 対象の年月、連勤の上限などの共通ルール |
| ② | シフト種別 | 早番・遅番などの種類、時間帯、必要人数 |
| ③ | スタッフ管理 | 名前、公休数、有給、担当できるシフト、個人の希望 |
| ④ | 希望休入力 | 休みの希望と、出勤を決めておくシフトを入れる |

| ⑥ | シフト表 | できた表を確認・手直し・Excel出力 |

## 5. どうやってシフトを作っているか

### 大事な順に、1つずつ「ゼロ」を目指します

全部のルールを一度に満たそうとすると、計算が終わりません。
そこで **大事な順に並べて、1つずつ片付けていきます。**

```
第1段  コンプラ（6連勤以上） ← まずここをゼロにする（連勤上限の設定に関係なく）
第2段  人員・役職           ← 第1段を崩さずに、ここもゼロにする
第3段  公休・有給           ← 第1・2段を崩さずに…
第4段  連勤・遅→早
第5段  単発出勤・定数
  ↓ ここから下は、「ルールごとの強弱」で「絶対」にしたものを先に解く
第6段〜 リズム（休みの間隔・早遅の切替）／早遅の希望／土日休み／休み方／
        連休の回数／早遅バランス／単発休み／上下関係
```

**一度達成した段は、その後の段で崩しません。**
「ルールごとの強弱」で「絶対」にしたルールは、第5段のすぐ後に、「できれば」のルールより先に解きます。
だから「人が足りない」「公休が足りない」といった重大なルールが、
後から細かい希望のために壊されることがありません。

生成後の画面に出る「段階ごとの結果」は、この各段の結果です。

### 同時に何通りも試して、一番良いものを採用します

シフト作りは、探し方によって結果がぶれます。
そこで **解き方を少しずつ変えた計算を、パソコンのCPUの数だけ同時に走らせて、
一番エラーが少なかった結果を採用** しています。

「一番良い」は次の順で比べます。
① 6連勤以上（コンプラ違反）の回数 → ② 人員不足 → ③ 「絶対」の件数（連勤は回数で数える）
→ ④ 連勤の上限を超えた日数 → ⑤ 公休の足りない日数の合計 → ⑥ 早遅の切り替えの超過回数（「絶対」のとき）
→ ⑦ 「できれば」の件数

一番良いものを選ぶので、1通りだけで解くより悪くなることはありません。
選んだ答えには、最後に「入れ替えて減らせる所」を自動で直す仕上げをかけます
（「絶対」の種類も、連勤の超過日数も、6連勤以上も増やさない入れ替えだけを使います）。
（基本設定の「複数パターンを同時に試す」でオフにもできます）

### 生成には2種類あります

| ボタン | 時間 | 中身 |
|---|---|---|
| 1分生成（最大60秒） | 最大60秒 | 1部門あたり最大60秒で探し、見つかったいちばん良い表を返す（いちばん良い表かどうかは確かめない）。設定を試行錯誤する用 |
| じっくり生成（最大約11分） | 最大約11分 | 中で1分生成の答えも作り、良いほうを採る。各段を最後まで計算しきれたら「計算完了」と出る（大事な順に1つずつ、今の設定ではこれ以上減らせないことを計算の上で確かめたもの。大事な順に確かめるので、エラーの件数の合計がいちばん少ないとは限らない）。計算しきれなかった段があれば「時間内でいちばん良い答え」と出る。最終確定用 |

21人以上の部門は、時間を短くするため「ほぼ最良（差2%以内）」のところで計算を止めるので、「時間内でいちばん良い答え」になり、
「妥協なしで再計算（早期停止を無効・最大約11分）」のボタンが出ます。

じっくり生成では、次の2つの文も出ます。

| 画面の文 | 意味 |
|---|---|
| 「1分生成の答えのほうが良かったので、そちらを採りました」 | じっくり生成の答えと1分生成の答えを画面と同じ並べ方で比べ、1分生成のほうが良かった（じっくり生成の側が時間内に計算しきれなかったときは、そのことも知らせる） |
| 「画面の検査で悪くなる答えを外して、良いほうを採りました」 | 時間切れではない。計算の途中で、画面の検査では悪くなる答えを外した。外した段があるので「これ以上良い組み合わせは無い」とまでは確認していない |

計算のあいだは、ほかのアプリや重いページを閉じてください。パソコンが混むと、同じ時間で探せる量が減り、表が悪くなることがあります。

## 6. 守っているルールの一覧

ルールは「絶対 / できれば / OFF」の3段階で調整できます（①基本設定の「詳しい設定」→「ルールごとの強弱」）。
ルールの名前は、エラーの一覧に出る名前と同じです。下は、はじめの強さです。

### はじめから「絶対」のもの

- 人員不足・公休数不足・連勤超過・担当外シフト・日ごとに要るスキル（この5つは変えられません）
- **6連勤以上はコンプライアンス違反（5連勤まで可）**。連勤上限の設定に関係なく、
  6日以上続いたら必ず違反として扱う（6連勤以上 として分けて出す・自動生成でも避ける・前月末からの連勤と半休も数える）
- 遅→早（休みなし）（遅番の翌日に早番）・夜勤明けの出勤・単発出勤（前後が休みの1日だけの出勤）
- 責任者・総務の重複（1日1人だけの役）・責任者の順位（同じ時間帯に上の役職の人がいるのに、下の人が責任者）
- 副店長不在（副店長が2人以上いる店で、副店長がだれも出勤せず、早責・遅責もチーフ以上でそろっていない日。副店長が1人の店では数えない）
- スキル不足（最低人数に足りない）・早遅希望と不一致（③の早可／遅可）・行事日に対象者が休み

### はじめは「できれば」のもの

- 定数オーバー・スキル目標に不足
- 連勤中の時間帯切替・早遅の切り替え回数・遅→休→早（遅番 → 休み1日 → 早番）・連休が長すぎる
- 早遅バランスのずれ・土日休み希望・休み方の希望・遅→早は2連休（個人ルール）・連休の回数不足
- 特別日の副店長（入れ替え日は副店長のだれかが遅責、新装日は早責に入る。入れ替え日に早責では足りない）
- 有給の日数のずれ（①の「ルールごとの強弱」には出ません）
- 単発休み（①の「勤務のルール」の「単発休みのペナルティ」で決めます）

## 7. データはどこに保存されるか

### ⚠️ これは必ず読んでください

スタッフ名簿も、設定も、作ったシフト表も、
**使っている人のブラウザの中にだけ** 保存されています。

そのため、こうなります。

| こうすると | どうなる |
|---|---|
| 別のパソコンで開く | **何も入っていない** |
| 別のブラウザで開く | **何も入っていない** |
| ブラウザの「Cookie とサイトデータ」を削除 | **全部消える（元に戻せない）** |
| シークレットモードで使う | 閉じた瞬間に消える |

**同じパソコンを使う人が、悪気なくブラウザを掃除しただけで全部消えます。**

### 対策：「書き出し」を習慣に

シフトが完成したら、画面右上の **「データ」→「書き出し」** を押してファイルに保存してください。
設定もシフト表も全部入ります。**「データ」→「取り込み」** で完全に元に戻せます。

```
おすすめの運用
  1. シフトが完成したら必ず「データ」→「書き出し」
  2. ファイル名を月ごとに分ける（例：シフト_2026年09月.json）
  3. 会社の共有フォルダなど、消えない場所に保存する
```

**過去のシフトはアプリに残りません。** 書き出したファイルだけが記録になります。

## 8. 困ったときの対処

**上から順に試してください。プログラムの知識は要りません。**

| 症状 | 対処 |
|---|---|
| 画面が真っ白／表示がおかしい | `Ctrl` + `Shift` + `R` で再読み込み |
| 変更したのに反映されない | 同上（古い状態が残っているだけ） |
| エラーが多すぎる | ①の「詳しい設定」→「ルールごとの強弱」で、優先度の低いルールを「OFF」にする |
| エラーが多すぎる | じっくり生成 を試す（1分生成より減ることが多い。計算のあいだは、ほかのアプリや重いページを閉じる） |
| 生成が終わらない | 1分生成 に切り替える |
| 余（人員余り）が出た | ⑥シフト表の「その他の操作」→「余の解消」で、有給か出勤に振り替える |
| 何をしても直らない | [9. 直し方・公開のしかた](#9-直し方公開のしかた) の「前の状態に戻す」 |
| データが消えた | 「データ」→「取り込み」で、書き出したファイルを読み込む |

## 9. 直し方・公開のしかた

### どうやって公開されているか

このフォルダの中身は、**GitHub Pages** という仕組みで
そのままインターネット上に公開されています。

```
ここのファイルを更新  →  数分待つ  →  https://mumu140sr.github.io/-/ に反映
```

サーバーの操作は必要ありません。**ファイルを置き換えるだけです。**

### 🔧 前の状態に戻す（一番大事）

**不具合が出たら、まずこれを試してください。プログラムを読む必要はありません。**

1. https://github.com/mumu140sr/- を開く
2. ファイル一覧の上にある **「◯ commits」**（変更の履歴）をクリック
3. 戻したい日付の変更を選ぶ
4. 右上の「⋯」→ **「Revert」**（取り消し）を選ぶ
5. 5分ほど待ってからアプリを開き直し、`Ctrl` + `Shift` + `R`

**これでほとんどの不具合は回避できます。**

### 変更したときの決まりごと

プログラムを直す場合、**必ず守ってください。**

1. **`data.js` と `data.v6.js` を同じ内容にする**
   （`optimizer.js` と `optimizer.v6.js` も同様）
2. **`index.html` と各jsファイルの `?v=NNN` という番号を、全部1つ上げる**（どのファイルにあるかは CLAUDE.md に書いてあります）
   （これを忘れると、ブラウザが古い状態を使い続けて変更が反映されません）
3. 変更内容を日本語で記録して保存する

## 10. 引き継ぐ方へ

### まず、これだけ覚えてください

| | やること |
|---|---|
| **毎回** | シフト完成後に「データ」→「書き出し」でファイル保存 |
| **困ったら** | `Ctrl` + `Shift` + `R` → ルールをOFF → じっくり生成 |
| **壊れたら** | GitHub で前の状態に戻す（[手順](#-前の状態に戻す一番大事)） |

**この3つで、9割の場面は乗り切れます。**

### 覚えておくと安心なこと

- **このアプリは勝手に壊れません。** サーバーがないので、放っておいても動き続けます。
  不具合の原因は、ほぼ100%「誰かが変更したこと」です。
  **完成したら触らない、が一番安全です。**

- **設定でできることは意外と多いです。** スタッフの追加・必要人数の変更・
  シフト種別の追加・ルールのON/OFFは、すべて画面から変更できます。
  **プログラムを触る必要はありません。**

- **リポジトリを触れる人を、2人以上にしておいてください。**
  1人しかいないと、その人が不在のとき誰も対応できません。

### 連絡先

プログラムの修正が必要になったときの連絡先を、ここに書いておいてください。

```
担当者：
連絡先：
外部委託先（あれば）：
```

## 技術的な補足（分かる方向け）

- **構成**：フレームワークなしの素の HTML / CSS / JavaScript（約15,000行）
- **計算エンジン**：HiGHS（WebAssembly版）をリポジトリ内に同梱
- **計算方式**：全ルールをソフト制約（違反に罰点）とした混合整数計画問題を、
  段階最適化（辞書式）で解く。各段の達成値を上限として次段に引き継ぐ。
  近傍探索（local branching）と、解き方を変えた複数同時実行を併用。
- **重い計算は Web Worker** で実行し、画面が固まらないようにしている
- **保存先**：`localStorage`（キー：`shiftAppData`）
- **外部通信**：Excel出力ライブラリ（cdn.jsdelivr.net）のみ。
  シフトのデータを外部に送信する処理は一切ない。
